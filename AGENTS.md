# Agent guide

gbos-builder: a small, readable, source-built Googlebook OS (Android 17 desktop) port for the
MSI Modern 15 B7M, developed in QEMU first. Human documentation: [README.md](README.md).
The priority is that a person can understand how to build, update and deploy it, not the fewest lines.

## Start here

1. Read [docs/specs/README.md](docs/specs/README.md) — one spec per component with its status,
   settled decisions, pitfalls and next actions.
2. Read the spec for the component you are changing. Its **Decisions** are settled; reopening one
   needs the user's agreement.
3. Before handing back, update only the documentation affected by this change. For component
   work, update its spec (status, actions, handoff-log entry); the `/handoff` prompt does this.

## Working with the owner

- This is a personal project. Prioritize readable code, simple builds and good performance on this
  machine; do not add release, compatibility or contributor machinery without a real need.
- For a guided review, explain one change at a time: why, what code does, and how to verify it.
  Make only that change, show the result and pause for the owner's feedback before moving on.
- A clear request to implement a change is approval for that change. A question or a roadmap is
  not blanket approval to implement every idea in it.
- Prefer a short explanation, focused diff and relevant test over process-heavy handoffs. Update a
  component spec when the change affects its status, decisions or next action.
- Proactively capture verified, reusable findings in the relevant skills or specs, and make small,
  directly related tool or development-speed improvements without a separate owner request.
  Keep these evidence-driven and scoped to the task, not speculative frameworks or unrelated
  cleanup. Existing validation approvals, long-build approvals and safety boundaries still apply;
  discuss larger changes or behavior changes first.
- Commit focused, verified milestones without a separate reminder, including owner-confirmed
  hardware fixes. Review the diff, exclude unrelated changes and generated/private files, and
  leave unverified work uncommitted. Do not push or rewrite history without permission.
- Aim for descriptive commit subjects around 60-72 characters and body lines around 80.
  These are guidelines, not hard limits: favor natural phrasing, but avoid very long lines.
  Separate the subject and body with a blank line; leave URLs and trailers intact.

## Learning and choosing an approach

- The owner values understanding and maintainable choices, not just achieving the immediate
  goal. A passing test establishes behavior, not that the approach is the best fit.
- During guided reviews, explain one decision at a time: why it exists, alternatives,
  trade-offs and verification. Pause for feedback before edits.
- Before adding custom integration, search upstream documentation, source, releases and
  relevant external projects, as well as local references. Do not limit investigation to
  the repository or send private code, logs or credentials to external services.
- Present existing solutions first. Explain the verified compatibility gap before proposing
  custom code; distinguish findings from assumptions.
- Prefer adopting or minimally adapting maintained solutions over reinventing them.
  Optimize for less code we must understand and maintain.
- Preserve the working baseline. Recommend changes only for a concrete benefit; do not
  chase perfection or turn reviews into unsolicited rewrites.

## Ground rules

- **Upstream first; patch only when necessary.** Each patch or custom file must be maintained when
  upstream or Google's image changes, so keep them to a minimum. Before writing one, try in order:
  upstream code unchanged; a pinned upstream release or commit that already has the fix;
  upstream settings (kernel config, build options, properties, command line, QEMU options);
  removing or adding whole files. Patch only when none of these work. Keep the patch small;
  its header says why it is needed and when it can be dropped. Do not
  reformat or tidy upstream code. When a pin changes, drop patches that upstream now covers.
- **Source, not binary edits.** No byte-offset patches or edited executables. Google's image
  changes only through declared lists and patches under [android/](android/) and explicitly
  selected [hardware recipes](hardware/): `remove.list`, `install.list`, `patches.list` and
  their native recipe fragments per target, applied by
  [scripts/android-overlay.sh](scripts/android-overlay.sh). Other components change through
  source patches (for example [mesa-drm-master.patch](hardware/drivers/drm-handoff/mesa-drm-master.patch)).
- **Patch files, not programs that write changes.** When a Google text file must change, use a
  `.patch` generated by `diff -u` from Google's original; add or delete whole files through the
  lists. Never put change logic in Python or ad-hoc scripts; Python is for build tools and checks.
- **Official prebuilts where they fit; build only what we change.** Use an official upstream
  prebuilt unchanged when one does the job (Google's recovery image, kernel toolchain, QEMU kernel
  modules, NDK and emulator KeyMint/Gatekeeper). Build from source only what we patch or what has
  no suitable prebuilt, and say why next to its pin in [sources.mk](sources.mk). Every download is
  pinned there by version and SHA-256.
- **Preserve behavior and safeguards.** Never drop path checks, metadata checks or error reporting
  to shorten code or make a build pass. A regression needs a focused test as well as a fix.
- **Out of scope unless the user asks:** KernelSU/root, dual boot, installers, GPU passthrough.
- **Never write block devices or physical disks.** Never delete or recreate `out/android/disk.img`
  (Android's data) or `out/src/` trees (may hold uncommitted source edits) without asking.
- **Keep SELinux enforcing;** no permissive domains or broad policy changes.

## Readability, build speed and performance

- Prefer a clear 20 lines over a clever 5: descriptive names, explicit inputs and straightforward
  control flow. Keep scripts single-purpose; avoid speculative frameworks and unnecessary helpers.
- Follow the surrounding indentation, naming and quoting. Use existing tools and patterns;
  do not introduce a formatter or dependency just for style, or reformat unrelated code.
- Explain non-obvious reasons: upstream quirks, Android requirements and metadata preservation.
  Do not narrate obvious commands or add comments merely to repeat the code.
- Keep documentation short and link to the code instead of repeating it. Put language-specific
  details in [.github/instructions/](.github/instructions/).
- **Slow first build, fast repeat builds.** Keep everything that can be reused: downloads, source
  trees, toolchains and build directories, named by a hash of their inputs. A repeat build
  redoes only work whose inputs changed; an unchanged build takes seconds and writes nothing.
  Measure build time separately from guest startup or UI performance.
- Before optimizing runtime, measure the bottleneck and compare the smallest practical options.
  Keep the working softpipe setup as a fallback until the faster path is verified.

## Build and test

Everything compiles inside the Debian builder container ([scripts/builder.sh](scripts/builder.sh));
the host needs Docker, make, Python 3 and `/dev/kvm`.

```sh
make                       # list targets
make test                  # unit tests: fast, no disks, no network
make qemu JOBS=12          # build what changed and boot; VNC on localhost:5900
make qemu-check JOBS=12    # bounded full boot; evidence in out/qemu/
make console COMMAND='getprop sys.boot_completed'   # while the VM runs
```

- This machine has 12 CPUs: use `JOBS=12`. A first GKI build takes about an hour; ask before
  starting long builds or downloads.
- Stop the VM before `make android-image`: the disk lock rejects updates while it runs.
- Unchanged inputs must rebuild nothing and write no disk partitions — keep it that way.
- Use checks proportional to the change: unit tests for logic, image rebuild for image changes,
  QEMU boot for boot/runtime changes. Documentation-only changes need link checks, not a full build.

## Verifying honestly

- "Boots" means a usable screen with working input, confirmed by looking at a screenshot — not
  `sys.boot_completed`, a serial shell, a logo, or a correctly sized PNG.
- Report what was tested and what was not. Untested is not working.
- Say what you actually checked and what remains unverified. Keep useful evidence in the session
  or ignored `out/`; do not claim a test or boot from a commit message alone.
- For a behavior-preserving build refactor, compare rebuilt outputs with a known baseline,
  including metadata, and check that a second build preserves timestamps and writes no partitions.
- Over the serial shell, filter on the guest (`logcat -d -s Tag | tail -n 200`); unbounded
  `logcat -b all` can wedge the console.

## Keep the repository safe

- Check the worktree before editing; preserve unrelated changes and review the diff before staging.
- Keep generated files in ignored `out/`. Never write physical disks or delete
  `out/android/disk.img` or editable `out/src/` trees without explicit permission.
- Clean up only temporary files and processes created for this task. Never include secrets or
  generated images in a commit.
- Keep commits focused; do not amend, rewrite history or push unless asked.
